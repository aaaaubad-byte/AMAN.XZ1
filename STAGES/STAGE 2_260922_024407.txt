15. ATOMIC PROTECTION APPROVAL

Implement a trusted transaction-safe database operation for accepting a protection request.

The final function name/signature may be chosen after examining the actual Supabase structure.

The operation must logically perform:

• Verify the caller is authorized.

• Lock/validate the target request as necessary.

• Verify the request is still pending.

• Validate customer/number ownership.

• Validate provider relationship.

• Validate plan relationship.

• Validate payment information according to the database contract.

• Prevent an overlapping active protection.

• Change request status to approved.

• Create the protection.

• Preserve historical price/duration values.

• Determine start date.

• Determine end date.

• Check task settings.

• Create the first task if enabled.

• Create the appropriate notification.

• Create the audit log.

• Commit everything atomically.

If any required operation fails:

ROLL BACK THE TRANSACTION.

There must not be a partially approved request.

Examples that must be protected against:

Approve twice Concurrent approve Approve after rejection Approve request while conflicting protection exists Protection creation failure after request approval Task creation failure after protection creation Audit/notification failure causing inconsistent state 

The exact transaction design must follow the actual database capabilities.

16. REQUEST REJECTION

• Verify authorization.

• Verify request is still pending.

• Save rejection reason.

• Save reviewing manager/actor.

• Save review timestamp.

• Change status to rejected.

• Create customer notification.

• Create audit log.

• Never create a protection.

• Preserve transaction integrity.

Rejecting an already approved/rejected request must fail safely.

19. FIRST TASK CREATION

When protection approval creates a protection:

• Read the applicable provider's task settings.

• Determine whether the first task is enabled.

• If disabled: 

• do not create a first task.

• If enabled: 

• create the first task.

• Snapshot the applicable task amount/settings needed for historical integrity.

• Link the task to the protection and customer number.

• Keep task creation inside the appropriate transaction where required.

Creating a task must not automatically mean sending a customer notification unless the documented notification rules require it.

20. RECURRING TASK CREATION

Implement the trusted database operation required to create the next task.

When a task is completed:

• Verify authorization.

• Verify task is eligible for completion.

• Record completion.

• Check whether recurring tasks are enabled.

• Calculate the next due date.

• Verify the protection still permits a next task.

• Create the next task when required.

• Snapshot the applicable amount/settings.

• Audit the operation.

If recurring tasks are disabled:

Do not create another task.

Protect the operation against duplicate completion and duplicate next-task creation.
