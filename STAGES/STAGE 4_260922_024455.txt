1. Objective

Implement the complete AMAN Administration Application/UI and connect it to the real backend implemented in Stages 1–3.

The administrator must be able to securely operate the AMAN system through real database operations.

The Administration layer must support the administrative functionality defined in AMAN.XZ.txt, including:

• Secure administrator authentication.

• Administration dashboard.

• Customer management.

• Customer phone-number visibility where authorized.

• Protection-request management.

• Protection approval/rejection.

• Protection management.

• Telecom-provider management.

• Protection-plan management.

• Payment-method management.

• Payment-task management.

• Task completion/rescheduling/cancellation where authorized.

• System settings.

• Task settings.

• Notifications where required.

• Audit/history visibility where explicitly allowed.

• Administrative account/security management.

Do not invent additional administrative roles or organizational hierarchies.

2. Administrative Security Is Backend-Enforced

The Administration application must NEVER rely on UI visibility as its security mechanism.

Administrative authorization must be enforced through:

• Supabase Auth.

• Database/RLS.

• Secure RPC/database functions.

• Backend authorization checks.

A user must not become an administrator simply because the Android application displays an Admin screen.

Never trust:

• Client-side role values.

• Local flags.

• Hardcoded admin IDs.

• Hidden UI routes.

• Shared secrets embedded in the APK.

3. Administrator Authentication

Implement a dedicated administration authentication flow.

The administrator must authenticate using the real Supabase authentication system.

Do not create:

• Fake admin sessions.

• Hardcoded administrator credentials.

• Fake access tokens.

• Local-only admin authentication.

• Secret admin passwords inside the APK.

After successful authentication:

• Verify that the authenticated account is actually authorized for administration.

• Load the administrative application.

• Reject unauthorized accounts.

If authorization fails:

• Do not display administrative data.

• Return the user to the authentication flow.

• Show a clear authorization message.

4. Single Manager / Administrator Model

Follow the model established by AMAN.XZ.txt and Stage 2.

Do NOT introduce:

• SUPER_ADMIN.

• OPERATIONS.

• FINANCE.

• SUPPORT.

• EMPLOYEE hierarchy.

• Multiple invented administrator roles.

If the backend defines a single authorized AMAN manager/administrator, preserve that model.

Any existing role/authorization structure must be verified against the actual Stage 2 implementation before changing it.

12. Approve Protection Request

Approval MUST use the secure backend/RPC workflow implemented during Stage 2.

The Android client must NOT independently perform a sequence of separate inserts such as:

UPDATE request INSERT payment INSERT protection INSERT subscription INSERT task 

unless those operations are explicitly part of the secure backend contract.

The preferred operation is the atomic approval RPC implemented in Stage 2.

The approval operation must guarantee the required transaction behavior.

13. Atomic Approval

When approving a valid pending protection request, the backend workflow must perform the required operations atomically according to the Stage 2 design.

This may include:

• Validate request.

• Verify PENDING state.

• Validate payment reference.

• Change request to APPROVED.

• Create customer payment record.

• Create protection.

• Create subscription/protection record as defined by the actual schema.

• Create first payment task.

• Create financial transaction where required.

• Create state-transition log.

• Create audit log.

• Create customer notification.

If any required operation fails:

ROLL BACK THE TRANSACTION.

The UI must report the failure.

It must not display a false success message.

14. Approval Idempotency

The administrator must not be able to accidentally create duplicate protections by:

• Double clicking.

• Retrying.

• Reopening a request.

• Sending the same approval twice.

The database/RPC layer is the final protection against duplicate approval.

The Android UI should also disable the action while the request is processing.

Do not rely on a local Android boolean/Set as the only duplicate-prevention mechanism.

15. Reject Protection Request

Implement rejection through the secure backend contract.

A request can be rejected only when its current state allows rejection.

The administrator should provide a rejection reason where required.

The operation must:

• Change the request to REJECTED.

• Preserve the reason.

• Record audit/history information.

• Create the required customer notification.

A rejected request must NOT create:

• Active protection.

• Subscription/protection record.

• Payment task.

16. Invalid State Transitions

The UI must not allow invalid operations.

Examples:

• Approving an already approved request.

• Rejecting an already rejected request.

• Approving a rejected request.

• Completing a cancelled task.

• Cancelling a completed task.

However, backend/database state-transition rules remain authoritative.

The UI is only the first layer.
